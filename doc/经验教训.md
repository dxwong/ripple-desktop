# 开发经验教训（持续更新）

## 1. 协议解析：不要手写 buffer

**场景**：手动读取 HTTP chunk，用 `\n\n` 分割 SSE 事件。

**教训**：手写 buffer 解析几乎必定出错——半包粘包、编码错位、`\r\n`/`\n` 混用、边界溢出，每一种都是折磨。

**正确做法**：
- Python: 用 `aiohttp.StreamReader.readline()`，不要用 `read(N)` + 自己 split
- 需要全功能 SSE 解析：用社区包 `sseclient-py`、`aiohttp-sse-client`
- 总之：协议层面的 chunk/event 解析，交给库，不手写

## 2. Bug 调式：先加日志，再修 Bug

**场景**：字词重复、输出空白、无限等待三个问题反复出现。

**教训**：不要猜测 Bug 原因，不要靠"我觉得可能是 X"，先加日志看到实际数据。
正确的流程：
1. 在**每个关键步骤**加 INFO 级别日志（开始、结束、成功、失败）
2. 运行一次，看日志定根因
3. 修完确认日志显示正确流程
4. 再清理不必要的调试日志

**日志要回答的问题**：
- 卡在哪一步？→ 看最近一条日志是什么
- 数据流到哪里断了？→ 看收发的数据内容
- 异常是什么？→ 看错误日志的 traceback

---

## 3. 数据源选择：全局总线 vs 私有通道

**场景**：opencode serve 的 `/event` 是全局事件总线，`/session/{id}/message` 的 POST 响应体是个 SSE 流。

**教训**：
- 全局总线混入其他 session 的事件 → 字词重复
- POST 响应体才是当前请求的私有通道

但要注意：**连接到私有通道的时间点必须正确**。
- ❌ 先 POST 再连 `/event` → 错过事件
- ✅ 先连 `/event` 再 POST → 不错过任何事件

**原则**：订阅必须在发布之前，否则丢失数据。

---

## 4. 异步 IO：必须设超时

**场景**：`readline()` 没有 timeout，服务端不结束就永远卡死。

**教训**：所有 IO 操作都必须带超时，不管看起来多安全：
```python
# ❌ 危险：无限阻塞
raw = await resp.content.readline()

# ✅ 安全：最多等 30 秒
raw = await asyncio.wait_for(resp.content.readline(), timeout=30.0)
```

---

## 5. Session 生命周期：用完必须检测结束

**场景**：模型处理完不会关闭 `/event` 连接，而是发一个 `session.status (type=idle)` 事件。

**教训**：不要等连接关闭来判断结束，要监听业务层的结束信号（idle 事件、`[DONE]` 标记等）。

## 6. Windows 编码：GBK 吞掉你的日志

**场景**：`UnicodeEncodeError: 'gbk' codec can't encode character` → 日志静默丢失 → 调试时啥也看不到。

**教训**：Windows 终端默认 GBK，打日志需要处理编码：
```python
_handler = logging.StreamHandler(sys.stdout)
_handler.setFormatter(...)
# 关键：设置编码错误处理
sys.stdout = open(sys.stdout.fileno(), mode='w', encoding='utf-8', buffering=1)
```

或者在启动时设置环境变量：
```bash
set PYTHONIOENCODING=utf-8
```

## 7. 问题范围：先确认是自己的 Bug 还是环境问题

**场景**："换个大模型也一样" 或 "同样的代码别人没问题"。

**教训**：先自测确认基础环境正常：
- 手动用 curl/postman 调用 API 看响应格式
- 写一个最小可复现脚本跑通基本流程
- 再用这个脚本替换复杂的业务逻辑逐步二分排查

不要在大系统里猜，先在小范围证实/证伪。

## 8. `useEffect` async cleanup 竞态 → 双重监听 → token 重复

**✅ 已修复 (2026-05-14)。这是「重叠词 bug」的最终根因。**

**场景**：流式对话中 UI 显示 "用户用户 询问询问 我我 是什么是什么"——每个 token 出现两次相邻拼接。桥梁直连测试输出干净（0 重复），确认问题在 Tauri IPC 层。

**根因**：`useBridge.ts` 的 `useEffect` 中 `setupListeners` 是 async 函数（`await import` + `await listen`），但 cleanup 同步执行。在 React StrictMode 的 `挂载→清理→挂载` 循环中：

```
T1: 第一次 setupListeners() 启动 → await import (挂起)
T2: cleanup 执行 → unlistenRef = [] → 没东西可清理！
T3: 第二次 setupListeners() 启动 → await import (挂起)
T4: 第一次 await 完成 → 注册 listener-A
T5: 第二次 await 完成 → 注册 listener-B
结果: 两个 bridge-message 监听器同时生效
```

每个 `bridge-message` 事件触发两次回调 → 每个 token 被 `appendToConversation` 两次 → 重叠词。

**修复**：在 `setupListeners` 内加 `cancelled` 标志：
```typescript
let cancelled = false;
// cleanup: cancelled = true
// 每个 await 后: if (cancelled) { unlisten(); return; }
```

**教训**：
- async 函数在 `useEffect` 中必须处理 cleanup 竞态
- React StrictMode 是发现此类 bug 的好工具——它会让 bug 稳定复现
- **修复此 bug 时曾误判为其他原因**：先改了 bridge SSE 解析、前端闭包过期、ChatMessage 条件渲染，直到加拦截日志 `[bridge→UI] #N chunk` 才确认 chunk 到达前端时已经重复了一次
- 此 bug 与之前的 `conversations` 闭包过期是同一类问题——都是 `useEffect`/`useCallback` 的异步闭包与 React 生命周期的交互

## 9. opencode serve API：POST 响应是 JSON，不是 SSE

**场景**：2026-05-14 调试流式对话重复词 bug，假设 POST `/session/{id}/message` 的响应体是 SSE 流，直接读 `resp.content.readline()` 解析 token。结果 content-type 是 `application/json`，读到的第一行是 JSON 确认消息，流立即关闭，0 token。

**教训**：
- 做架构假设前先验证。POST 响应体用 `await resp.text()` 读出来看实际格式
- opencode serve 的 SSE 流只能从 `/event` 端点获取，POST 只是触发模型处理并返回 JSON 确认
- `方案评估_OpenCode流式集成.md` 文档中"POST 响应体是 SSE 流"的说法是错的——那是设计假设，不是实测结论

**正确做法**：
```
1. 连 /event → 订阅 SSE 流（全局事件总线）
2. POST /session/{id}/message → 触发模型（响应 JSON，消费掉）
3. 等 /event 流结束 → 发 ok
```

## 10. Python `__pycache__`：改了 .py 但进程跑的可能是旧 .pyc

**场景**：改了 `bridge_server.py`，重启电脑，但桥接日志中新的 `[流式]` 标记一行都不出现。怀疑文件没保存、路径不对、Python 版本不对……最终发现是 `bridge/__pycache__/bridge_server.cpython-312.pyc` 缓存了旧字节码。虽然作为主脚本不应读缓存，但在多次导入测试中，`.pyc` 的 mtime 比 `.py` 更新，Python 优先加载了 `.pyc`。

**教训**：
- 修改 Python 文件后，删除对应的 `__pycache__/*.pyc`
- 或者启动前 `python -m py_compile` 强制重编译
- Windows 环境下 Python 缓存行为可能与预期不同（多次 import 测试会更新 .pyc mtime）

**检查方法**：
```bash
python -c "import os; d='bridge/__pycache__'; print(os.path.getmtime('bridge/bridge_server.py')); [print(f, os.path.getmtime(os.path.join(d,f))) for f in os.listdir(d)]"
```

## 11. Bug 修复纪律：一次一个，先记后修

**场景**：在修「流式输出重复词」bug 的过程中，同时改了 bridge SSE 解析、前端闭包过期、bridge 事件监听竞态三个问题，导致：UI 完全不输出（回退监听修复时引入新 bug）、无法确定哪个修改解决了哪个问题、调试方向反复横跳。

**教训**：
1. **先读文档**：`DEVELOPMENT.md` 记录了已知问题、架构决策、踩坑历史。改代码前先读完相关文档。
2. **看到 bug 先记录，别急修**：在 `DEVELOPMENT.md` 的「未解决 / 待办」中添加条目，写清现象和初步判断，然后继续当前任务。
3. **一次只修一个 bug**：确认修复有效后再修下一个。不要"顺便修"——顺便修的几乎必定引入新问题。
4. **修前写预期、修后验证**：改之前明确"改完后应该看到什么现象"，改完后对照验证。
5. **核心代码改动必须记录**：改了 bridge、Rust、前端核心逻辑，立即更新 DEVELOPING.md 和 经验教训.md，附上**具体改动内容 + 原因 + 回退方法**。

**反例（本次）**：
```
修复 A（bridge SSE 解析）→ 无效 → 修复 B（前端闭包）→ 部分有效
→ 修复 C（bridge 监听竞态）→ UI 完全不输出 → 回退 C
→ 回到 A，发现 POST 响应是 JSON 不是 SSE → 重做 A
→ 发现桥接直连测试正常，UI 仍重复 → 方向迷失
```

**正例**：
```
1. 记录 bug：UI 显示重叠词"有什么有什么"
2. 写最小复现脚本直连 bridge → 确认 bridge 输出干净（32 token，0 重复）
3. 结论：bug 在 Tauri IPC 或前端，不在 Python bridge
4. 缩小范围到前端 token 拼接逻辑或 Rust 事件转发
5. 逐个排查，每步验证
```

## 12. 异步 useEffect cleanup 竞态（旧条目，已并入 #8）

**场景**：`useEffect` 中的 `setupListeners` 是 async 函数（`await import` + `await listen`），但 cleanup 是同步的。React StrictMode 下：

```
第一轮挂载 → setupListeners() 启动 → await... (挂起)
  → cleanup 执行 → unlistenRef 还是 [] → 什么都没清理
第二轮挂载 → setupListeners() 启动 → await... (挂起)
第一轮恢复 → listen 完成 → 注册监听器 A
第二轮恢复 → listen 完成 → 注册监听器 B
结果：两个监听器同时生效 → 事件处理两次 → token 重复
```

**教训**：
- async 函数在 useEffect 中需要 `cancelled` / `mounted` 标志
- cleanup 设置标志 → async 回调中每步检查 → 已取消则清理并返回
- 注意：**修复此问题可能反而暴露其他 bug**（如修复后 UI 无输出），因为去掉了"重复监听"这个容错层

**但注意**：此问题是否真的导致当前重复词 bug，待验证。优先排查 buffer 累积方向。
